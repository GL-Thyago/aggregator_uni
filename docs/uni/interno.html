O que a Uni faz

A Uni é o aggregator. Os cassinos falam só com você. A Salsa fala só com você. Os cassinos não conhecem a Salsa.

Baixar Markdown Baixar HTML

Peças

PeçaPapel
Cassino (cliente Uni)Tem os jogadores e o saldo. Chama a API Uni. Expõe o wallet.
Uni (este sistema)Catálogo, sessão, launch, publisher XML, débito no wallet certo.
SalsaEstúdio dos jogos. Abre o iframe e, na aposta, chama o publisher da Uni.

Como a comunicação funciona

1. Cassino → Uni POST /api/v1/uni/test/games/{slug}/launch (API Key + ID do jogador) 2. Uni cria uma sessão (token UUID) e devolve launchUrl da Salsa. 3. Cassino abre launchUrl no iframe. O jogador está na Salsa, com o token da Uni. 4. Salsa → Uni POST /api/v1/salsa/publisher (XML) GetAccountDetails, GetBalance, PlaceBet, AwardWinnings, RefundBet… 5. Uni → wallet do cassino daquela sessão POST {walletUrl}/balance POST {walletUrl}/spin
Um aggregator. Vários cassinos. Cada cliente Uni tem o próprio walletUrl. A sessão guarda o cliente: aposta do cassino A nunca cai no wallet do cassino B.

URL que a Salsa deve ter cadastrada

Um publisher, test e live. A Salsa sempre chama:

https://rggames.site/api/v1/salsa/publisher

Não dê essa URL ao cassino. É só para a Salsa.

Test e live (por cassino, não no .env)

O ambiente fica no cadastro do cliente (admin Uni: Teste ou Produção). Um cassino em live não muda quando outro usa teste. SALSA_API_BASE / SALSA_LAUNCH_TYPE no .env não mandam mais no launch.

O cassino chama POST /api/v1/games/{slug}/launch. A Uni monta a URL Salsa certa para aquele cliente.

Rotas explícitas (staff / debug): /api/v1/uni/test/… e /api/v1/uni/live/….

Teste GPI (certificação Salsa)

Ferramenta da Salsa que bate no publisher e valida saldo, aposta, prêmio, reembolso, hash e token.

  1. Wallet do cassino público (nunca localhost no servidor).
  2. Jogador de teste com saldo.
  3. Launch:
POST https://rggames.site/api/v1/uni/test/games/gpi-validation/launch
X-Api-Key: sua-api-key

{ "externalUserId": "ID_DO_JOGADOR", "currency": "BRL" }

A resposta traz gpiUrl. Abra no browser. Ou:

https://gpi-validation-test.patagoniaentertainment.com/gpi-validation/execute
  ?token={sessionToken}
  &type=CHARGED
  &lang=pt
  &pn={SALSA_PN}
  &game=gpi-validation

Se um case falhar: GET /admin/v1/integrations/salsa/last-request com X-Admin-Key.

O wallet tem de aceitar crédito só de prêmio: betAmount = 0 e winAmount > 0.

Colocar jogos em produção (ex. OPS-3353)

  1. A Salsa libera o pacote no PN de produção (não é o aggregator que “cadastra” no estúdio).
  2. Na Uni, no boot ou em Publicar catálogo, os IDs entram no banco (ex. evo-oss-xs-monopoly-live). O endpoint de catálogo da Salsa traz o resto.
  3. No admin, o cassino que vai validar dinheiro real fica em Produção.
  4. Esse cassino abre o jogo com POST /api/v1/games/evo-oss-xs-monopoly-live/launch.
  5. Logs: publisher GET /admin/v1/integrations/salsa/last-request e logs do EasyPanel.

Sem PN de produção (SALSA_PN_LIVE), o launch live usa o PN de staging no host de produção e a Salsa responde “Non Existent Publisher”.
